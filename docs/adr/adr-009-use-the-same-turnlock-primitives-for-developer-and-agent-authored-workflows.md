# ADR-009: Use the same TURNLOCK primitives for developer-authored and coding-agent-authored workflows

- **Status:** Accepted
- **Date:** 2026-09-13
- **Decision order:** 009

## Context

After defining execution semantics, the product discussion turned to how TURNLOCK workflows are created. The target user is a developer working in a coding-agent environment, not a nontechnical user who requires a separate visual workflow builder.

A developer may already know the desired workflow precisely enough to write it. The same developer may instead describe the desired workflow to the coding agent and ask that agent to write or modify it. Coding agents are already capable code authors; TURNLOCK should give them a clear public workflow surface rather than invent a second privileged generation path.

If human-authored and agent-authored workflows use different semantic representations, TURNLOCK would create unnecessary product complexity and make generated workflows harder for developers to inspect, own, and modify. Likewise, if the only practical authoring path requires a proprietary builder, TURNLOCK would move away from the developer-native environment in which the product is meant to live.

## Decision

TURNLOCK workflows are authored from a common set of **TURNLOCK workflow primitives** into the same class of developer-readable workflow artifact, regardless of whether the immediate author is a developer or a coding agent.

The intended authoring paths are:

```text
developer intent
  → developer writes workflow with TURNLOCK primitives

or

developer intent
  → coding agent writes workflow with TURNLOCK primitives

both
  → same semantic workflow artifact
  → same execution semantics
```

TURNLOCK MUST NOT define a privileged hidden workflow representation used only by coding agents for ordinary authoring.

TURNLOCK MUST NOT require a graphical/no-code builder to express the core workflow execution model. Higher-level authoring tools may exist later, but they must compile/project to the same underlying artifact and semantics available to direct code authors.

This ADR does **not** select the concrete authoring language, library, file format, type system, package format, or complete primitive set.

## Rationale

The user already has two capable authoring actors in the same development environment: themselves and their coding agent. TURNLOCK's job is to expose good primitives and reliable execution semantics, not to duplicate the coding agent with a separate AI workflow generator product.

A shared artifact also keeps ownership clear. A workflow generated by the coding agent remains ordinary code the developer can inspect, edit, review, diff, version, and ask the agent to modify again.

The abstraction boundary is therefore:

```text
natural-language or direct developer intent
            ↓
ordinary code authoring
            ↓
TURNLOCK primitives
            ↓
workflow artifact
            ↓
TURNLOCK execution semantics
```

## Consequences

- Developer-authored and coding-agent-authored workflows have one semantic model.
- Generated workflows remain directly inspectable and editable by developers.
- TURNLOCK needs a sufficiently clear public primitive surface for coding agents to use reliably.
- A future visual editor, template system, or higher-level generator is optional and subordinate to the same artifact model.
- Workflow authoring remains developer experience rather than becoming a separate end-user workflow-builder product.

## Alternatives considered

### Build a dedicated AI workflow generator with a private representation

Rejected as the core model. The coding agent already serves as an AI code author, and a private representation would create a second semantic path developers cannot naturally own or edit.

### Require a visual/no-code builder

Rejected as a core requirement. It is unnecessary for the initial developer/coding-agent audience and would make a separate UI product part of the critical path for expressing TURNLOCK semantics.

### Support human-authored code and agent-authored workflows as distinct artifact types

Rejected. It would create avoidable translation, debugging, and ownership boundaries between two authors operating in the same development environment.

## Verification obligation

A proposed authoring API is conformant only if a representative workflow can be produced both by direct developer authoring and by a coding agent using the public TURNLOCK surface, with both results remaining the same semantic artifact class and executing under the same runtime semantics.
